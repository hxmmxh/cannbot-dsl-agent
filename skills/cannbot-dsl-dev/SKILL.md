# CANNBot DSL 开发入口

读取用户请求、项目指引和已有代码，先确定执行方式，再加载相应能力。沿用已明确的环境、交付目录与验收标准；仅询问会影响实现或验证的必要缺项。

## 直接开发

数学语义和支持范围清楚、实现规模有限、能用独立参考验证，且任务没有要求完整设计交付、独立验收或性能调优时，使用 [直接开发流程](references/direct-development.md)。简单 demo、教学样例和局部修复通常适用。

由主会话直接实现、运行测试并自检，按需使用 `cannbot-dsl-env-check`、`cannbot-dsl-best-practice`、`ops-precision-standard` 等原子 Skill。此分支不加载 `ops-direct-invoke` 的 PM 入口，也不启动其模板、资源快照或 harness。

是否适用根据实际支持域、同步与资源设计、验证方式和交付要求判断；需要真实 NPU 精度验证本身不要求完整编排。

## 调用原版完整工作流

用户明确要求完整工作流、结构化规格或设计交付、独立验收、性能调优，或任务需要复杂同步、多实现单元协作和阶段交接时，读取已安装的 `ops-direct-invoke` Skill，并按它的原始流程组织任务。

入口位于项目 `.agents/skills/ops-direct-invoke/SKILL.md`；配置由 `.cannbot/ops-direct-invoke.json` 定位。尚未安装时按项目说明运行 `bash install.sh`。

完整流程的角色、模板、任务契约、审批和恢复规则均由上游维护。本地直接开发的简化约定不应用到已选的上游节点；不复制或改写上游入口、模板及任务文件。

## 任务切换与交付

- 复用仍有效的环境证据；候选实现、独立参考、用例与实际测试结果对应同一交付版本。
- 主会话的检查称为自检；独立验收由完整流程的独立角色完成。
- 恢复已有工作流时沿用原版公开恢复接口。用户要求改为直接开发时，先通过公开接口停止活动运行并保留记录，再进入本地流程。
- 直接开发中发现需要扩大协作或交付范围时，保留已有代码与证据，说明原因后转入完整流程；只对缺失的必要决定或授权补充确认。
- 个人行为定制维护在本仓库 `skills/`。三个 `third_party/` submodule 及其安装资源保持原样。
