# 直接开发

适用于 `cannbot-dsl-dev` 入口判定的小范围任务。由主会话连续完成下面的工作，不创建 `context.json`、资源快照、独立 Git 仓或 execute/verifier 会话，也不运行模板引导、组装器和 harness。

## 对齐并复用环境

从请求、项目指引和已有记录确定数学定义、公开接口、必要的 shape/dtype、精度标准、实际解释器、CANN、目标设备与交付位置。信息充分时用简短进度说明概括，不另写需求分析、结构化 spec 和多份设计文档。未指定的常规实现选择在任务授权内决定，标明适用范围。

按项目约定激活指定环境。已有适配同一解释器、DSL/CANN 版本和目标设备的环境通过记录，且无变化证据时直接复用；仅补查缺失或变化项。首次检查或有变化时，调用对应原子环境 Skill 的真实入口，不先启动编排。环境通过仍不能代替当前算子的上板测试。

## 实现并验证

读取实际语言与实现问题需要的知识和本地 API/样例；DSL 使用 `cannbot-dsl-best-practice`，精度沿用目标工程 checker 或 `ops-precision-standard`，已有更严格阈值继续保持。只展开与当前代码有关的参考，不加载完整方案、Unit 拆分或正式测试生成能力来完成简单样例。

直接在用户指定的代码目录编写最小实现。固定小输入可采用简单调度，不为演示引入通用 tiling、多级流水或额外框架。沿用已有测试入口；无入口时用最小 pytest 或独立脚本，CPU Golden 与候选分开。无需生成三组 CSV、Unit YAML 或 Git bundle，除非用户或目标仓明确要求这些交付件。

用例覆盖用户主场景，以及能发现当前实现主要错误的一小组输入。例如全 1 Add 之外，用不同输入、含负数的一例检查两路输入的实际读取；不把该例固定为所有算子的测试要求。需要真机通过时，无可用设备必须失败并如实说明，不能跳过后宣称通过。

在选定解释器和真实设备上运行所需测试，检查进程退出码、实际执行例数、当前源码与结果对应关系及误差。保留原始命令、日志和逐例结果；首次设备初始化与编译较慢时，报告实际阶段，避免重复启动探针。代码变化后仅重跑受影响验证，已有证据充分时不再重复全量运行。

## 检查并交付

主会话就地检查输入契约、计算路径、输出覆盖和测试判定，结果称为自检。使用一份 README 或现有使用文档说明接口、限制、复现命令和实际结果；日志、缓存与结果汇总放在项目约定的 build 或任务记录目录。

通常只需源码、独立参考与小用例、运行说明和原始证据。不因存在导出装饰器就增加 Native 发布与冷/热缓存验证，不自行增加性能采集或调优；需要额外交付时按用户范围组织。

实现中发现需要复杂同步、多单元协作或需求范围发生实质变化时，保留可用代码与证据，说明升级理由并转入原版完整工作流；仅在缺少必要决定或授权时询问用户。直接开发没有 harness 节点状态，不伪造完整流程或独立验收结论。
